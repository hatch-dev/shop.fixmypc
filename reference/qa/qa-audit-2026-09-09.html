Authentication & access control

6 findings · 3 critical

The most urgent item in this report is SEC-01. It needs no credentials, no session and no user interaction — only an admin's email address, which is published on the site.

SEC-01Critical

Any admin account can be taken over by an unauthenticated request

app/Http/Controllers/AdminsController.php:998 · routes/api.php:301 (outside auth:admin)

POST /api/admin/verify-code accepts email, code and password, compares the code with !=, and on a match writes a new password hash. Three of the four admins in this database have never used forgot-password, so their stored code is NULL. In PHP 8, null == 0 is true — and Laravel's required rule accepts the integer 0. A JSON body carrying "code": 0 therefore satisfies both the validator and the comparison. 

# resets the password of any admin whose code is NULL
POST /api/admin/verify-code
Content-Type: application/json

{"email":"admin@…", "code":0, "password":"attacker-chosen"}

Even where a code is set, it is a 4-digit rand(1000,9999) that is never cleared after use and has no expiry — kilcock@fixmypc.ie still carries 7896 from a past reset. With the default throttle:api of 60/min the whole keyspace falls in under three hours from a single IP.

Fix Compare with === against a string, reject null/empty codes outright, hash and expire codes (reuse the PasswordResetToken model already written for customers — it does all of this correctly), clear on use, and rate-limit by email. Rotate all four admin passwords now.
SEC-02Critical

Guest identity is a browser-generated random string the server never issues or checks

frontend-panel/store/user.js:48 · app/Http/Middleware/OptionalAuth.php

Guest sessions are keyed on user_token, generated client-side from Math.random() and accepted verbatim by every guest endpoint. The server never issues it, never validates it and never binds it to a session, so it functions as a bearer credential that anyone can guess or forge. 

token = Math.random().toString(36).slice(2,5)
      + (+new Date * Math.random()).toString(36).substring(0,12)
      + Math.random().toString(36).slice(2,5)

Presenting an arbitrary token grants read and write on that guest's cart, saved addresses, orders (order/by-user), cancellations and order emails. V8's Math.random() is xorshift128+ and recoverable from observed output; the date component narrows the space further.

Fix Issue guest tokens server-side with Str::random(40), store them in the guest_users table, and return them in an HttpOnly cookie. Reject any token the server did not issue.
SEC-03High

Installer and maintenance endpoints are reachable without authentication

routes/api.php:212–218, 178–201

GET /api/migration runs migrate plus db:seed against the production database with no guard at all. GET /api/update-env rewrites .env; GET /api/read-update-log returns file contents; GET /api/clear-cache flushes config and cache. POST /api/test-otp sends a Twilio SMS to any phone number supplied and returns the OTP in the response body — free SMS at your expense, and an oracle for anyone probing the OTP flow. fresh-migration and create-user (which would drop every table) are held back only by SHARED_SERVER_CONFIGURED=true in .env.

Fix Delete the test routes, move installer routes behind auth:admin or strip them from production builds, and never gate destructive operations on an env flag alone.
SEC-04High

Debug mode is on in production, exposing database credentials on any error

.env

APP_ENV=local and APP_DEBUG=true with APP_URL=https://shop.fixmypc.ie. Any unhandled exception renders an Ignition page containing the full stack trace, source excerpts and the environment block — including DB_PASSWORD and the payment gateway secrets. Several endpoints in this report return $e->getMessage() straight to the client regardless of debug state.

Fix Set APP_ENV=production, APP_DEBUG=false, and replace raw getMessage() responses with logged errors and a generic message.
SEC-05Medium

Checkout payload encryption uses a hardcoded key and static IV shipped to the browser

app/Models/Helper/Utils.php:352

Checkout parameters travel in an AES-128-CBC blob whose key and IV are compiled into both the server and the client bundle. It provides no confidentiality and no integrity — it is obfuscation, and it is worth naming because order_method, voucher, points_discount, orderId and transactionId all arrive inside it and are trusted as though the wrapper authenticated them.

Fix Drop the wrapper — TLS already covers transport. Validate and re-derive every value server-side rather than trusting the payload.
SEC-06Medium

SVG uploads accepted, and filenames collide under concurrency

app/Models/Helper/FileHelper.php:307 · Validation.php:1104, 1158

mimes:jpeg,png,gif,svg,webp admits SVG, which executes script when served inline from the storefront origin — stored XSS against any admin viewing the product. Filenames are built as prefix-time()-mt_rand(1,9).ext: two uploads in the same second collide one time in nine, silently overwriting another product's image. One upload rule ('file' => 'required') sets no type or size limit at all, and the extension is taken from the client.

Fix Drop svg (or sanitise and serve Content-Disposition: attachment), use Str::uuid() for filenames, derive the extension from the detected MIME type, and give every upload rule explicit mimes and max.

Payments

5 findings · 3 critical

POST /api/v1/order/payment-done is the single point where an order becomes paid. For four of the nine gateways it performs no verification whatsoever. There are no webhook endpoints anywhere in the route table, so this client-driven call is the only confirmation path that exists.

PAY-01Critical

PayPal and SumUp orders are marked paid without contacting the gateway

app/Http/Controllers/OrdersController.php:1325, 1338

} else if ((int)$request->order_method == …PAYPAL) {
    $paymentDone = true;          // no capture check, no amount check

} else if ((int)$request->order_method == …SUMUP) {
    $paymentDone = true;          // same

A customer who reaches checkout can call payment-done for their own order with order_method set to PayPal or SumUp and receive goods for free. Nothing verifies that a transaction exists, that it succeeded, or that its amount matches the order.

Fix Capture and verify server-side against the gateway, compare the captured amount and currency to orders.total_amount, and set payment_done only on a match.
PAY-02Critical

Razorpay is confirmed by echoing back a token the client already holds

app/Http/Controllers/OrdersController.php:1329

The only check is $order->payment_token != $request->payment_token. That token is the Razorpay order id, handed to the browser in the checkout response before any payment occurs. Replaying it marks the order paid. Razorpay's razorpay_signature — the HMAC that actually proves payment — is never requested and never verified.

Fix Verify razorpay_signature with the SDK's utility->verifyPaymentSignature() over razorpay_order_id|razorpay_payment_id, then re-fetch the payment and confirm its amount.
PAY-03Critical

A Flutterwave logging failure is treated as a successful payment

app/Http/Controllers/OrdersController.php:1310

} catch (\Exception $e) {
    if (str_contains($e->getMessage(), 'The stream or file')) {
        $paymentDone = true;      // unwritable log file ⇒ "paid"
    }

This branch fires when the Flutterwave SDK cannot open its log file — a filesystem permission problem — and converts it into a successful payment. Any exception whose message happens to contain that phrase, including one raised before verification is attempted, produces the same result.

Fix Remove the branch. Fix the log path in the SDK config and let verification failures fail.
PAY-04High

Stripe recomputes its own total, drops discounts, and truncates cents

app/Http/Controllers/OrdersController.php:1341–1385

The Stripe branch rebuilds the total from ordered_products instead of using the stored total_amount, and its formula includes only the voucher — flash discounts and loyalty points are silently omitted, so the card is charged more than the order records. The amount is then converted with (int)($totalPrice * 100), which truncates: 

total 1.15  → Charge amount 114 cents   (expected 115)
total 10.10 → Charge amount 1010 cents  ok
total 46.20 → Charge amount 4620 cents  ok

The call also uses the legacy \Stripe\Charge::create with a raw source token. That API predates SCA and will be declined for most European cards — material for an Irish storefront.

Fix Migrate to PaymentIntents, charge (int) round($total * 100), and take the figure from total_amount so one number governs the whole order.
PAY-05Medium

payment-done is not idempotent and accepts a client-supplied transaction id

app/Http/Controllers/OrdersController.php:1196, 1138

Nothing checks whether the order is already paid, so repeat calls re-run the whole branch — on Stripe that means a second charge. Separately, POST /api/v1/order/transaction writes any trans_id the client sends, and order creation accepts client-supplied orderId and transactionId verbatim, letting a caller choose their own order number.

Fix Return early when payment_done is already set, and derive transaction ids from gateway responses only.

Pricing, discounts and tax

10 findings · 2 critical

The storefront and the server calculate the total independently and disagree. The customer is shown one figure and charged another — this is happening in live orders today.

MON-01Critical

Flash discounts and loyalty points are deducted on screen but never from the amount charged

app/Http/Controllers/OrdersController.php:2114–2230 · frontend-panel/pages/checkout.vue:410

The storefront shows productPrice − voucher − flashDiscount (points subtracted alongside). Every one of the nine server-side payment branches stores the same expression: 'total_amount' => $totalPrice - $offeredVoucher. The flash discount is written to ordered_flash_discount and the points are debited from the customer's balance — but neither reduces what is charged.

Live evidence — order 65

id  total_amount  computed  voucher  flash_disc
65  1646.00       1646.00   0.00     200.00

customer was shown €1,446.00 — charged €1,646.00

Order 62 is worse still: total_amount of 316.00 against line items summing to 521.00 and a recorded discount of 75.75, which reconciles to nothing.

Fix Compute the payable total once — $totalPrice - $offeredVoucher - $flashDiscountAmount - $pointsDiscount, floored at zero — assign it to a variable before the payment branches, and use that single variable for total_amount, $re['amount'] and every gateway call.
CPN-01Critical

The voucher expiry check can never fire, so expired coupons are accepted at checkout

app/Http/Controllers/OrdersController.php:1650

if ($start >= $now && $now >= $end) {   // requires start ≥ now ≥ end
    return … voucher_expired
}

The condition is only satisfiable when start >= end, which no real voucher satisfies. Every expired and every not-yet-started voucher passes. The coupon preview endpoint gets it right ($start < $now && $now < $end), so the two disagree — a customer told "expired" on the cart page succeeds by submitting anyway. 

voucher window                          checkout   preview
expired (ended 5d ago)                  ACCEPT     REJECT
active  (ends in 5d)                    ACCEPT     ACCEPT
future  (starts in 5d)                  ACCEPT     REJECT

Live exposure Two published vouchers are exploitable right now:

FIRSTOFFER  €15 flat   min €100   expired 2024-12-04
TEST5       €500 flat  cap €10    expired 2026-05-31
Fix Invert to if ($now < $start || $now > $end). Better, extract one Voucher::validFor($user, $subtotal) method and call it from both endpoints so they cannot drift again.
TAX-01High

VAT is charged only when excludeVAT = 1 — the flag reads backwards

app/Http/Controllers/OrdersController.php:1849

$excludeVAT = Product::where(['id' => …])->value('excludeVAT');
if ($taxRule && $excludeVAT == 1) {     // tax added when "exclude" is set

Tax is applied only to products flagged as excluded, and skipped for everything else. In the live catalogue that is 9 products taxed and 112 untaxed — VAT is not being collected on 93% of the range, while the 9 flagged products have 23% added on top of the price shown on their product page.

Fix Decide the intended meaning, then rename the column to match it — vat_exempt with the condition inverted, most likely. Reconcile past orders with your accountant before changing it, since the correction alters historical VAT liability.
TAX-02High

The 23% rate is hardcoded against tax_rule_id == 1

app/Http/Controllers/ProductsController.php:604–612

if($tax_rule_id==1){
    $vatInclusivePrice = $selling_price + $selling_price*23/100;

The tax_rules table already holds the rate (VAT23, type percent, price 23) and a second rule (VAT Margin, 0%) that this code cannot express. Add a 13.5% or 9% Irish rate and the stored VAT-inclusive price will be wrong; edit rule 1's rate and nothing recalculates.

Consequence in live data The stored values are already inconsistent:

id        title                  selling  vatInclusive  vatInclusiveOffered
99492285  Samsung Galaxy A54 5G  1000.00  1230.00       1230.00
99492284  Samsung Galaxy A05s    1000.00  1230.00       0.00   ← offer 1000.00
99492293  Ram Upgrade-64GB         49.00  0.00          0.00   ← never computed

CART-01High

The cart writes client-supplied prices straight to the database

app/Http/Controllers/CartsController.php:260, 361 · app/Models/Cart.php:13

$request['voucher_discount'] = $request->original_price - $request->price;
$cart = Cart::create($request->all());

// Cart::$fillable includes: price, original_price, voucher_code, voucher_discount

Any caller can set price, original_price and voucher_discount to arbitrary values. The order total is recomputed from the product record so the charge itself holds, but these values are copied into ordered_products_inventories.price and product_voucher_discount_applied — the rows that feed admin reporting and reconciliation. Sending price without original_price also stores a negative discount.

Fix Remove the four columns from $fillable and derive them server-side from the product and the applied voucher.
CPN-02Medium

Coupon preview trusts a client-supplied cart value

app/Http/Controllers/VouchersController.php:56, 92, 145

validity() takes $request->price as the cart total. The server-side recalculation is commented out directly above. A caller who sends a large price clears any min_spend gate and, for percentage vouchers, is shown a discount computed from their own number. The preview also computes on a total including shipping while checkout computes on a total excluding it, so the two figures differ for every percentage voucher even when used honestly. The endpoint additionally writes to the cart while claiming to validate.

Fix Restore the server-side subtotal (the commented block), and make the endpoint read-only.
CPN-03Medium

apply_type is enforced at preview but not at checkout

VouchersController.php:31 vs OrdersController.php:1598

The preview filters where('apply_type', 1); the checkout query does not. Voucher TEST5 (apply_type = 2, a product-level code) is rejected on the cart page and accepted at checkout.

Fix Apply the same filter in both queries.
CPN-04Medium

Voucher caps are truncated to whole units

OrdersController.php:1663 · VouchersController.php:151

$offeredVoucher = (int)$voucher->capped_price;

cap €10.99 → discount applied €10
cap €25.50 → discount applied €25
cap  €0.99 → discount applied  €0
Fix Cast to (float) and round to 2dp.
CPN-05Medium

Voucher usage counts include failed and cancelled orders, and race under load

OrdersController.php:1613, 1638

Both usage_limit and limit_per_customer are enforced with Order::where('voucher_id', …)->count(), which counts unpaid, abandoned and cancelled orders — a customer whose card is declined burns their single-use code. The count is also read outside any lock, so concurrent redemptions of a last-remaining code all pass.

Fix Count only paid, non-cancelled orders, and take a row lock on the voucher for the redemption.
PRC-01Medium

A variant price silently cancels flash sales and offer prices

OrdersController.php:1795–1808

The price ladder is inventory > flash > offered > selling, so any variant carrying its own price beats every discount. Put a variant product into a flash sale and customers pay the variant price with no indication the sale did not apply. The same function also tests the flash price two different ways in its two loops — $flashPrice > 0 when checking voucher minimum spend, $flashPrice !== null when charging — so a €0.00 flash price is read differently within one request.

Fix Decide precedence deliberately (a flash price should normally win), extract it into one Product::currentPrice($inventory) method, and call it from both loops and the storefront.
PRC-02Medium

Offer price is unvalidated and four €0.00 products are live on the storefront

app/Models/Helper/Validation.php:741 · ProductsController.php:591

productMain() validates selling as numeric|min:0|not_in:0 but says nothing about offered — no numeric check, no lte:selling. An "offer" above the selling price is accepted and charged. Meanwhile five products carry selling = 0.00 despite that rule, four of them with status = 1 and purchasable now: Storage Upgrade, Ram Upgrade, Storage Upgrade-128GB, Ram Upgrade-16GB — created through a path that bypasses productMain().

Fix Add offered => nullable|numeric|min:0|lte:selling, and route bulk import, duplicate and upsell creation through the same validator.

Inventory & stock

4 findings · 3 high
STK-01High

Checkout never compares the quantity ordered against the quantity in stock

OrdersController.php:1680 · CartsController.php:340

if ((int)$c->updated_inventory->quantity < 1 &&
    (int)$c->updated_inventory->is_active !== 1) { … out of stock }

Two problems in one line. The && means a product at zero stock passes whenever is_active is set, and $c->quantity — the amount actually being bought — never enters the comparison at all. Add-to-cart does check available stock, but only when merging into an existing cart row; the branch that creates a new row has no check whatsoever. One request adding 100 units of a 5-unit line therefore succeeds and completes checkout, leaving stock at −95.

The three negative rows currently in updated_inventories (−13, −2, −1) are all backorder-enabled lines, so those are by design — but the guard against genuine oversell is absent.

Fix Check $c->quantity > $inventory->quantity && !$inventory->is_active in both places, inside the transaction, with a row lock.
STK-02High

Cart quantity accepts negative numbers, which create stock out of nothing

app/Models/Helper/Validation.php:795

The rule is 'quantity' => 'required' — no integer, no min:1. Order creation then calls UpdatedInventory::decrement('quantity', $cart->quantity), and Laravel's decrement with a negative argument increments. Verified against the live schema (rolled back): 

inventory 62 before: qty=6
decrement(quantity, -5)
inventory 62 after : qty=11   ← stock created from nothing

A negative line also subtracts from the order total, and no floor is applied before the amount reaches the gateway.

Fix 'quantity' => 'required|integer|min:1|max:…', and floor the payable total at zero.
STK-03High

Stock is deducted before payment, and the one rollback that exists deletes the wrong rows

OrdersController.php:1900, 2166–2180

decrement runs while the order is still unpaid. Of the nine payment branches only Razorpay attempts to restore stock on failure, and that loop is wrong: 

$ops = OrderedProduct::where('order_id', $order->id)->get();  // immediately overwritten

foreach ($existingCart as $ops) {
    OrderedProduct::where('id', $ops->id)->delete();   // cart id used as ordered_product id
    UpdatedInventory::where('id', $ops->inventory_id)->increment('quantity', $ops->quantity);
}

The loop variable shadows the query result and then deletes ordered_products rows whose ids happen to match cart ids — unrelated rows from other orders — while the real ones survive as orphans. Every other failure path (abandoned Stripe, closed browser, declined card) leaves the deduction in place permanently.

Fix Reserve stock rather than deducting it, commit the deduction on confirmed payment, and expire reservations on a schedule. At minimum, fix the loop and give every failure branch the same rollback.
STK-04Medium

Variants that have ever been ordered can never be removed

app/Http/Controllers/UpdatedInventoriesController.php:58–74

Any inventory id present in ordered_products and absent from the submitted list blocks the entire save with a generic "inventory in use" message — there is no way to retire a discontinued variant, and no indication of which one is blocking. The check also relies on array_search(...) > -1, which reads as a false-vs-int comparison and only behaves because array_unique preserves keys.

Fix Soft-delete retired variants (historical orders keep their reference), and name the blocking variant in the error.

A third of live orders contain no line items

OrdersController.php:1786

Every item in the checkout loop is wrapped in if ($cart->shipping_place_id && !is_null($cart->product_inner)). When a cart row has no shipping place selected it is skipped silently — and if that is true of every row, the order is still created, still returned to the customer as a success, and still recorded with total_amount = 0.00.

RFN-01High

"Refund" flips a boolean and moves no money

app/Http/Controllers/CancellationsController.php:18

Customers can mark their own cancellation refunded

CancellationsController.php:183 · app/Models/Cancellation.php:16

Cancellation::create($request->all());
// Cancellation::$fillable = ['order_id','user_id','title','message','refunded','user_token']

POST /api/v1/cancellation/cancel-order is customer-facing. Including "refunded": 1 in the body writes it straight through, and the admin refunds queue then shows the request as already settled.

ORD-01High

Cancelling an order changes nothing except a flag

CancellationsController.php:157 · OrdersController.php:760

cancelOrder sets cancelled = true and leaves status untouched, so the order stays PENDING in every admin list and report. Stock is not returned, points are not reversed, and the voucher redemption is not released. The admin-side updateStatus has the same gap in the other direction — no restoration on any status change. Order 40 is in this state now: cancelled=1, status=1 (PENDING).

The root cause is the status enum itself: PENDING, CONFIRMED, PICKED_UP, ON_THE_WAY, DELIVERED. There is no CANCELLED, RETURNED or REFUNDED state, which is why cancellation had to become a parallel boolean.

Fix Add the missing states to config/constants.php, and centralise transitions in one method that restores stock, reverses points and releases the voucher.
ADM-01High

Order deletion has no permission check and leaves orphaned records everywhere

OrdersController.php:807

delete() checks only $this->isVendor — the Utils::userCan($this->user, 'order.delete') guard that every sibling method carries is missing, so any admin role reaches it. It removes ordered_products and cancellations, then the order, leaving ordered_products_inventories, ordered_voucher, ordered_flash_discount and point_transactions pointing at a row that no longer exists. Stock is not restored and it accepts a comma-separated id list, so one call can wipe many orders. There is no soft delete and no audit trail.

Fix Add the permission check, soft-delete instead of hard-delete, and cascade or clean the child tables.

"Buy now" deselects every cart in the database, for every customer

app/Http/Controllers/CartsController.php:263

Cart delete, select and shipping-update accept any row id without an ownership check

First-time guest checkout dereferences a null user record

ORD-03Medium

Order status accepts any integer, and bundle items are taxed

Validation.php:68 · OrdersController.php:1862

Validation::orderStatus() requires only id — status and payment_done are unvalidated, so status can be set to any value or moved backwards from DELIVERED, and the response reports payment_done: 1 whether or not that was written. Separately, tax is computed as $taxQtyOffer * $cart->quantity while the goods price uses quantity - bundleQtyOffer — so free bundle items are charged VAT. The flash discount base has the mirror-image problem: it sums product.selling rather than the price actually paid, so the discount is calculated off list price.

Fix Validate status with Rule::in(array_values(config('constants.orderStatus'))), apply the bundle offset to tax, and base the flash discount on the charged price.

Customer accounts & email

4 findings

Worth saying plainly: the customer password reset flow (PasswordResetToken) is well built — throttled, single-use, expiring, and it invalidates sessions on reset. It is the model the admin flow in SEC-01 should adopt.

EML-01High

Order confirmation emails are only sent if the browser stays open long enough to ask

routes/api.php:1019 · OrdersController.php:2309

Order creation sends no mail. The confirmation depends on the client calling GET /api/v1/order/send-order-email/{id} after the fact. A closed tab, a dropped connection or a payment redirect that does not return means the customer never hears from you — and there is no queue, no retry and no record of whether it went.

The endpoint has no ownership check either: it takes any order id, so ids can be enumerated to trigger repeat mail to their real owners. It is a GET with a side effect, so a prefetch or crawler resends it, and $order->guest_user->email is dereferenced without a null guard.

Fix Dispatch a queued mailable from order creation, verify ownership on any manual resend, and make the resend a POST.
EML-02Medium

No email on any status change

OrdersController.php:760

Signup verification codes are brute-forceable and the reset flow enumerates accounts

UsersController.php:876 (verify), 786 (forgot)

verify() compares with == and has no attempt limit beyond the global 60/min. Registration codes are 6 digits (a deliberate widening, per the comment in MailHelper), but the other flows remain at rand(1000,9999). forgotPassword returns a distinct "does not exist" message for unknown addresses, confirming which emails hold accounts.

Fix Compare with ===, count failed attempts per account and lock after five, and return the same response whether or not the address is known.
ACC-02Medium

Loyalty points are credited before payment and never reversed

OrdersController.php:1995

Points are written to point_transactions during order creation, before any gateway confirms. An abandoned or declined payment still earns them, and neither cancellation, refund nor order deletion debits them back. Points spent on an order that then fails are gone the same way — the debit is written up front with no compensating credit.

Fix Credit on confirmed payment, and reverse both directions in the cancellation and refund paths.

Missing by design, not by defect

Absent capabilities

These are not bugs in existing code — they are scenarios the system has no mechanism for at all, and several of the findings above are downstream of them.

Gateway webhooks

No webhook route exists for any provider. Payment confirmation depends entirely on the customer's browser completing a round trip, which is why PAY-01 through PAY-03 matter so much.

Stock reservation

Stock is one mutable integer with no ledger and no locking. Two shoppers can buy the last unit simultaneously, and there is no way to reconcile a discrepancy after the fact.

Checkout idempotency

No idempotency key and no in-flight guard. A double-click or a retried request creates two orders and deducts stock twice.

Order status history

Status is a single column that is overwritten. There is no record of who changed what or when — nothing to audit after a dispute.

Partial cancellation and refund

Both are all-or-nothing at order level. A customer returning one item of four has no path through the system.

Decimal money handling

Every calculation runs through PHP floats with number_format at the edges. Use integer minor units or decimal casts end to end.

Automated tests

tests/ holds the two Laravel example stubs and nothing else. None of the arithmetic in this report has a regression test, so every fix risks a new one.

Auth rate limiting

Login, verify-code and forgot-password inherit the global throttle:api of 60/min with no per-account counter or lockout.
